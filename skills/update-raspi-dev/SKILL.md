# Update Raspi Dev

## 目的

- `raspi-dev` スキルを会話内容に合わせて更新する。
- 必要なら `go-impl` スキルも会話内容に合わせて更新する。
- 新しい知識を追加するだけでなく、重複、冗長、古くなった記述を整理する。
- `raspi-dev` をできるだけ薄く保ち、長期的に保守しやすい形を維持する。

## 対象

- `/workspace/ai/skills/{raspi-dev,go-impl,update-raspi-dev}`
- ホスト側では `/home/kamiy2743/workspace/ai/skills/...` に対応する。

## 基本方針

- まず現在の `raspi-dev` を読む。
- コンテナ前提やホストパスの読み替えは `raspi-dev` の共通コンテキストに集約する。
- Go 実装の責務分割、package 構成、handler / infra / domain の書き方のような汎用ルールは、`raspi-dev` ではなく `go-impl` を優先して更新する。
- 反映候補は、この会話で得た知識のうち、再利用価値があり、比較的安定しているものに限る。
- 一時的な観測結果、単発のログ断片、今だけの値は原則として入れない。
- 同じ意味の記述が既にある場合は追記せず、既存の記述を短く正確に書き換える。
- 共通事項は `SKILL.md`、プロジェクト固有の内容は `references/<project>/overview.md` に入れる。
- `go-impl` でも、メインの `SKILL.md` は薄く保ち、package ごとの詳細は `references/` に寄せる。
- 同じ内容を複数ファイルへ重複記載しない。
- 手順や確認コマンドは、恒常的に必要でない限り入れない。
- 長い経緯説明より、判断に必要な結論だけを残す。

## 更新手順

1. 会話から、新しく得られた知識、修正方針、注意点を抽出する。
2. それが `raspi-dev` に入れるべき安定情報か、`go-impl` に入れるべき汎用ルールかを判断する。
3. 追加先を決める。
   - Raspberry Pi 全体や workspace 共通なら `SKILL.md`
   - project 固有なら該当する `references/<project>/overview.md`
   - Go 実装全般に再利用できるなら `go-impl`
4. 既存記述と重なる箇所を探す。
5. 追記ではなく、可能なら既存記述を短く統合して置き換える。
6. 不要になった重複や冗長表現を削る。
7. `/home/codex/.codex/skills/` 側からも同じ内容として見えるか確認する。
8. 更新後に、`raspi-dev`, `go-impl`, `update-raspi-dev` が前より長くなりすぎていないか確認する。

## 何を入れるか

- よく再発する設計上の注意点
- 構成理解に効く安定した知識
- 実装や運用で繰り返し参照される前提
- AGENTS やコードから確認でき、将来も参照価値が高い事実

## 何を入れないか

- 単発の調査メモ
- 一時的な障害の生ログ
- 毎回コードを読めば分かる細かすぎる実装詳細
- 同じ意味の言い換え
- 将来変わりやすい値をただ列挙しただけの記述

## 圧縮ルール

- 箇条書きは短くする。
- 同じ文脈の項目はまとめる。
- 「背景説明」と「結論」がある場合は、原則として結論だけ残す。
- 例は本当に必要なときだけ 1 つに絞る。
- 参照先がある内容は、重複して再説明しない。

## 出力

- どこを更新したか
- 何を追加したか
- 何を削除または統合したか
- まだ `raspi-dev` や `go-impl` に入れないと判断したものがあれば、その理由
